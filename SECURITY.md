# Безопасность

Не размещайте секреты, реальные платежные данные или сведения пользователей в коде/PR.
При утечке немедленно отзовите ключ: удаление файла из HEAD не очищает Git-историю.

После создания репозитория используйте GitHub **Security → Report a vulnerability**, если
владелец включил private vulnerability reporting. До включения приватного канала не создавайте
публичный issue с эксплуатационными подробностями; запросите у владельца приватный контакт.

## Модель CI

Submission выполняется только через `pull_request` на одноразовом GitHub-hosted runner,
с `contents: read`, без переданных secrets, без сохранения checkout credentials и без общего
Maven cache. Доверенные POM, Wrapper, тесты и скрипты берутся из base SHA.
После проверки Git diff переносятся только обычные `.java` выбранной задачи.
Аннотационные процессоры отключены, выбранный модуль ограничивает объём запуска.
Время job и forked JVM ограничено. Self-hosted runners для чужого кода запрещены.

Нет `pull_request_target`, `workflow_run`, импорта артефактов пользовательского CI в
привилегированные jobs и автоматического merge. Подготовка draft изолирована от PR событий:
job генерации read-only, write token появляется только в отдельном доверенном opt-in job.

## Пределы

Проверка путей защищает сборочную конфигурацию от обычной подмены, но Java-код исполняется
с возможностями процесса: может обращаться в сеть, расходовать ресурсы и атаковать runner.
Это не sandbox. Не запускайте непроверенное чужое решение на своём компьютере.
GitHub token остаётся read-only, а контекст платформы не является секретным хранилищем.
Сохраняйте approval первого запуска fork workflows и ограничение прав в настройках GitHub.

`pull_request` может использовать предложенную в PR версию workflow. Автор может попытаться
заменить саму проверку, поэтому одни имена required checks не защищают от намеренной подмены YAML.
Владелец проверяет diff workflows до разрешения запуска; CODEOWNERS и обязательное review
защищают merge. Организационный ruleset с доверенным required workflow усилит эту границу,
если он доступен выбранному аккаунту. Не передавайте secrets в PR workflows даже при изменении YAML.
Злонамеренный код может подделывать отчёты JUnit, использовать пробелы тестов или содержать
гонки: открытые тесты дополняются ручным review, автоматического зачёта нет.

`validate_catalog.py` и `audit_publication.py` проверяют известные пути/паттерны секретов
и историю entrypoint первого задания. Это эвристики, не доказательство отсутствия всех
секретов или замаскированных решений. До push нужен ручной просмотр diff и staged files.
