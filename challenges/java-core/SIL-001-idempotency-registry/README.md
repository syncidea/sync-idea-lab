# SIL-001 · Одно событие — одна обработка в пределах TTL

**Middle · Java 21 · Concurrency / идемпотентность · 90 минут**

Версия контракта 1.0. [Навыки и критерии приёмки](challenge.json).

## Контекст

Платёжный сервис получает повторные уведомления. Перед обработкой он проверяет ключ события:
в течение TTL только один запрос с этим ключом должен получить разрешение.
Реализуйте небольшой реестр в памяти одного JVM-процесса.

## Контракт

```java
new IdempotencyRegistry(Duration ttl, Clock clock);
boolean tryAcquire(String key);
```

При первом обращении `tryAcquire` возвращает `true` и открывает окно `[now, now + ttl)`.
До конца окна повтор возвращает `false`, сохраняя прежнее время истечения.
Ровно в момент `now + ttl` и позже ключ снова доступен; успешное принятие открывает новое окно.
Время читается из переданного `Clock`. Используйте точность `Instant`/`Duration`, включая наносекунды.

Все обращения потокобезопасны: при одновременных попытках с одним ключом и неизменным
временем ровно одна возвращает `true`. Для разных ключей окна независимы.
Линеаризуемое поведение требуется при неизменном времени и при монотонном времени;
скачки часов назад вне контракта. В тестах время меняется между завершившимися группами запросов.

`ttl` и `clock` не могут быть `null` (`NullPointerException`). TTL строго положительный,
иначе `IllegalArgumentException`. `key == null` → `NullPointerException`;
`key.isBlank()` → `IllegalArgumentException`. Другие строки сравниваются через `String.equals`,
без `trim`, изменения регистра или нормализации. Экземпляры реестра независимы.

## Примеры

TTL = 10 секунд, ключ `payment-42`:

| Время относительно начала | Результат | Срок действия после вызова |
|---|---|---|
| 0 секунд | true | до 10 секунд |
| 9 секунд | false | до 10 секунд |
| 10 секунд | true | до 20 секунд |
| 10 секунд, повтор | false | до 20 секунд |

## Требования

Изменяйте только `src/main/java/**/*.java` этой задачи. Можно добавлять свои классы в том же
дереве. Сигнатуры публичного API сохраните. Зависимостей вне JDK не нужно.
Проверяются атомарность, работа со временем, валидация и независимость состояний.
Предварительно нужны Java collections, `java.time` и основы многопоточности.

## Граничные случаи

- TTL в одну наносекунду; повтор за наносекунду до истечения и точно на границе.
- Разные, но равные строки; строки с пробелами по краям; кириллица.
- Серия отклонённых попыток не сдвигает TTL.
- Одновременные обращения одного ключа в двух последовательных окнах.
- Некорректный аргумент не регистрируется.

## Критерии приёмки

Все публичные JUnit-тесты проходят на Java 21. Объясните в PR, где находится атомарная
операция и почему два потока не могут одновременно получить разрешение.
Зелёный прогон конкурентного теста не доказывает отсутствие всех гонок: потребуется review.

## Ограничения

Нет БД, Redis, сети, Docker, хранения между перезапусками и фоновых потоков.
Память пропорциональна числу уникальных ключей. Для базового решения очистка и ограничение размера не требуются.
Предполагается, что `clock.instant().plus(ttl)` представимо в `Instant`.
Глобальная блокировка допустима для базового решения; её цену объясните в PR.
Реестр не гарантирует exactly-once обработку платежа: после выдачи разрешения обработчик может упасть.

## Подсказка

Сначала зафиксируйте инвариант одного ключа: проверка срока и обновление состояния должны
выглядеть для других потоков как одна операция. Затем проверьте границу TTL.

## Усложнение

Необязательно: предложите очистку истёкших ключей без удаления свежей записи другого потока.
Опишите политику памяти и поведение при скачках часов. Изменение контракта обсуждается отдельно.
